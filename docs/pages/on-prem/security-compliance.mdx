# Security & Compliance

## Overview

Authenta On-Prem is designed with **security, privacy, and data isolation** at its core.
All processing occurs entirely within your infrastructure, ensuring that sensitive media content and detection results **never leave your environment**.

This page outlines Authenta's security architecture, offline design principles, credential handling, and compliance alignment.

## 1. Core Security Principles

Authenta follows five key principles for secure operation:

| Principle                 | Description                                                                                         |
| ------------------------- | ----------------------------------------------------------------------------------------------------- |
| **Data Residency**        | All files, results, and logs remain within your infrastructure                                       |
| **Offline Operation**     | Internet access is required only once (for image pull). After setup, Authenta runs fully air-gapped  |
| **Zero Telemetry**        | No data, metrics, or telemetry are transmitted to external servers                                    |
| **Isolated Components**   | All services communicate internally via a private Docker network                                     |
| **Enterprise Governance** | Designed to meet data protection, privacy, and audit standards required by enterprise clients        |

## 2. Data Isolation & Air-Gapped Operation

Authenta's on-prem architecture ensures complete **logical and physical isolation** from external networks.

### How Isolation Works

- All components (PostgreSQL, Authenta API Server, ML Task Runner) run on your local host system
- The system uses **internal container networking** only — no external APIs or DNS calls are made once running
- Once Docker images are pulled from AWS ECR (and the public `postgres` image), all functionality works **offline** indefinitely
- Outbound internet can be **fully disabled** or restricted by firewall rules after installation

### Verifying Offline Readiness

You can confirm Authenta's independence by:

```bash
docker compose ps
# stop outbound network
sudo ufw deny out to any
# verify job creation, upload, and inference still work end-to-end
```

Job processing continues to function even with no internet connectivity — confirming full isolation.

## 3. Credential Security

Authenta requires internet-facing credentials only once during setup, to authenticate against the private AWS ECR.

### AWS ECR Credentials

- Provided as read-only credentials, scoped only to the Authenta container registry
- Used to pull initial Docker images and perform future updates
- Can be safely revoked or rotated after image pull is complete
- Not required for daily operation

Example login (one-time):

```bash
aws ecr get-login-password --region us-east-1 \
| docker login --username AWS --password-stdin <AUTHENTA_ACCOUNT_ID>.dkr.ecr.us-east-1.amazonaws.com
```

> 🔐 **Best Practice:** Store credentials in a secret manager (AWS Secrets Manager, HashiCorp Vault, or internal vault system) and restrict access to authorized DevOps personnel only.

### Application Secrets

Unlike the one-time ECR credentials, the following secrets are used continuously and must be kept confidential and rotated periodically:

| Secret                    | Used by      | Purpose                                             |
| ---------------------------- | -------------- | ------------------------------------------------------ |
| `POSTGRES_PASSWORD`         | `postgres`, `api-server` | Database access                          |
| `AUTH_JWT_SECRET`           | `api-server`  | Signs user/session JWTs                                |
| `CRYPTO_ENCRYPTION_KEY`     | `api-server`  | At-rest encryption of sensitive fields                 |
| `WORKER_BOOTSTRAP_TOKEN`    | `api-server`, `ml-task-runner-gpu` | Authenticates worker registration  |

> The compose file ships with development placeholder values for all of these (clearly marked `-change-me` / `-dev`). Replace them with strong, unique secrets before any deployment beyond local testing.

## 4. Network Security

| Layer                   | Security Mechanism         | Description                                                                          |
| ----------------------- | --------------------------- | ------------------------------------------------------------------------------------------ |
| Container Communication | Docker internal network     | `api-server`, `postgres`, and `ml-task-runner-gpu` communicate on a private, non-exposed network |
| External Ports          | Optional                    | Only `api-server` (`8080`) and `postgres` (`5432`, for migrations/backups) are exposed by default, and can be restricted to admin IPs |
| Firewall Enforcement    | Recommended                 | Block all outbound internet traffic after setup                                             |
| TLS Support             | Recommended for exposed ports | Place `api-server` behind a TLS-terminating reverse proxy if accessed from outside the host  |

> 🧠 You may fully operate Authenta within a segmented VLAN or secure subnet to comply with internal network segregation policies. If `api-server` doesn't need to be reachable from outside the host, drop its `ports:` mapping entirely and access it only via the Docker network.

## 5. Access Control

Access to Authenta is governed through host, container, and application-level permissions.

| Area              | Control Mechanism                       | Recommendation                                                    |
| -------------------- | ------------------------------------------ | ---------------------------------------------------------------------- |
| Host OS             | Linux user permissions                     | Run Docker as a non-root user part of the `docker` group               |
| Authenta API        | JWT (users) / API keys / worker tokens     | Rotate `AUTH_JWT_SECRET` and revoke unused API keys periodically       |
| Worker Fleet        | `WORKER_BOOTSTRAP_TOKEN` + per-instance token | Treat the bootstrap token as a shared secret; rotate it if a worker is decommissioned |
| Database            | `POSTGRES_USER` / `POSTGRES_PASSWORD`      | Change default credentials before production use                       |
| Data Directory      | File system permissions                    | Restrict `./shared` to authorized users only                            |
| Platform Admin      | `platform_user_roles` (operator/admin/finance/support) | Grant the narrowest role needed for each administrator     |

## 6. Logging & Auditing

Authenta produces structured logs for transparency and traceability. No external telemetry or analytics are embedded.

### Log Categories

- **System Logs** — service startup, configuration, and runtime events
- **Job Logs** — job creation, worker leases, inference results, and error reports
- **Access Logs** — API authentication events (login, token refresh, worker registration)

You can forward logs to your enterprise monitoring or SIEM platform for compliance auditing.

Example log:

```json
{
  "level": "info",
  "timestamp": "2026-07-17T12:34:56Z",
  "service": "ml-task-runner",
  "event": "Job completion reported",
  "job_id": "101",
  "status": "success"
}
```

## 7. Compliance Alignment

Authenta's architecture aligns with key data protection and privacy frameworks commonly required by enterprise and government clients.

| Framework             | Relevance                                  | Compliance Measures                              |
| ---------------------- | --------------------------------------------- | ------------------------------------------------------ |
| GDPR (EU)              | Data residency, consent, and audit control    | 100% local processing; no external transfers            |
| ISO/IEC 27001          | Information security management               | Container isolation, credential control, logging        |
| SOC 2 Type II          | Confidentiality & availability                 | No external data handling or telemetry                  |
| NIST 800-53 / 800-171  | U.S. federal cybersecurity controls           | Network isolation, access controls, auditability        |
| HIPAA (U.S.)           | Protected health information handling         | Local-only processing, secure credentials                |

Authenta On-Prem does not transmit any personally identifiable information (PII) or client media outside your network, making it suitable for regulated and sensitive environments.

## 8. Model and Data Privacy

Authenta's AI models are encapsulated within Docker containers and are not modifiable or externally accessible:

- No outbound model telemetry or analytics
- No upload, retraining, or cloud inference dependencies
- Input and output data remain local at all times
- Models do not store or cache user-provided content beyond the job's own workspace

This guarantees data confidentiality and eliminates the risk of unintentional data leakage.

## 9. Recommended Hardening Steps

After installation, we recommend applying these additional controls:

| Category    | Recommendation                                                                                     |
| ------------- | -------------------------------------------------------------------------------------------------------- |
| Network      | Disable outbound traffic; whitelist only internal Docker communication; drop `api-server`/`postgres` port mappings if not needed externally |
| Credentials  | Rotate `POSTGRES_PASSWORD`, `AUTH_JWT_SECRET`, `CRYPTO_ENCRYPTION_KEY`, and `WORKER_BOOTSTRAP_TOKEN` quarterly |
| Containers   | Run Docker as non-root user where possible                                                              |
| Logs         | Centralize to internal ELK/Graylog server with secure retention policies                                |
| OS Security  | Keep host OS and Docker packages patched                                                                |
| Monitoring   | Periodically verify container integrity, uptime, and worker fleet health via `/api/v1/workers`          |

## 10. Security Incident Handling

In the unlikely event of a system issue or suspected compromise:

1. Stop all Authenta containers:
   ```bash
   docker compose down
   ```
2. Isolate the affected host(s) from the network
3. Review Docker and host logs for anomalies
4. Restore from your latest verified backup (see [Maintenance & Updates](/on-prem/maintenance-updates))
5. Contact Authenta Support for verification or guidance before re-enabling production processing

Authenta's support team will assist your engineers in verifying integrity and configuration.
