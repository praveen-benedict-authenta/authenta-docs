# Configuration

## Overview

Once Authenta On-Prem is successfully deployed, you can tailor its configuration to match your environment, network policies, and workload requirements.
This guide explains how to customize the Docker Compose services, environment variables, and data directories.

Authenta's configuration is lightweight and fully contained within its deployment package — no internet connection or cloud sync is required after the initial image pull.

## 1. Services

Authenta On-Prem is deployed as three services in a single `docker-compose.yml`:

| Service              | Description                                                | Use Case                                   |
| --------------------- | ----------------------------------------------------------- | ------------------------------------------- |
| `postgres`            | PostgreSQL database — backs the API server and job queue    | Always required                            |
| `api-server`           | Authenta API server — auth, jobs, worker fleet management  | Always required                            |
| `ml-task-runner-gpu`   | GPU-accelerated inference worker                            | Requires NVIDIA driver + Container Toolkit |

Start the full stack with:

```bash
docker compose up -d
```

## 2. Base Configuration

The ML Task Runner's configuration is defined using a YAML anchor for reusability:

```yaml
x-env: &env
  LOG_FORMAT: pretty
  LOG_LEVEL: DEBUG
  AUTHENTA_API_URL: http://api-server:8080
  WORKER_BOOTSTRAP_TOKEN: worker-bootstrap-token
  WORKER_INSTANCE_ID: worker-1
  WORKER_CAPABILITIES: ai-audio-detection,ai-image-detection,ai-video-detection,audio-splitter,document-forgery-detection,document-intelligence,ekyc-deepfake,face-embedding,face-intelligence,face-liveness-detection,face-similarity,faceswap-detection
  FILE_URI_PREFIX: /opt/authenta

x-ml-task-runner-configs: &ml-task-runner-configs
  volumes:
    - ./shared:/app/shared
    - ./demo-app/data:/app/data
```

> If you're scaling to more than one `ml-task-runner-gpu` replica, override `WORKER_INSTANCE_ID` per container instead of relying on the shared anchor value — see the [scaling caveat](/on-prem/architecture#scalability).

## 3. Service Configuration

### PostgreSQL Settings

| Parameter           | Description         | Default in `docker-compose.yml` |
| -------------------- | -------------------- | -------------------------------- |
| `POSTGRES_USER`      | Database user        | `authenta`                       |
| `POSTGRES_PASSWORD`  | Database password    | `authenta_dev_password`          |
| `POSTGRES_DB`        | Database name         | `authenta`                       |

```yaml
services:
  postgres:
    image: postgres:18-alpine
    environment:
      POSTGRES_USER: authenta
      POSTGRES_PASSWORD: authenta_dev_password
      POSTGRES_DB: authenta
    volumes:
      - postgres-data:/var/lib/postgresql/data
    ports:
      - '5432:5432'
    restart: unless-stopped
```

> Change `POSTGRES_PASSWORD` (and the matching `DATABASE_URL` on `api-server`) before any deployment beyond local testing.

### Authenta API Server Settings

| Parameter                 | Description                                                        | Required |
| --------------------------- | -------------------------------------------------------------------- | -------- |
| `DOMAIN`                    | Public hostname the API is served from                              | Yes      |
| `DATABASE_URL`              | Postgres connection string, pointing at the `postgres` service      | Yes      |
| `AUTH_JWT_SECRET`           | Secret used to sign JWT access tokens                                | Yes      |
| `CRYPTO_ENCRYPTION_KEY`     | Base64-encoded 32-byte key used for at-rest encryption               | Yes      |
| `WORKER_BOOTSTRAP_TOKEN`    | Shared token workers present when registering — must match the value configured on `ml-task-runner-gpu` | Yes |

```yaml
services:
  api-server:
    platform: linux/amd64
    image: <AUTHENTA_ACCOUNT_ID>.dkr.ecr.us-east-1.amazonaws.com/authenta-webapp:<tag>
    depends_on:
      - postgres
    environment:
      DOMAIN: localhost
      DATABASE_URL: postgres://authenta:authenta_dev_password@postgres:5432/authenta
      AUTH_JWT_SECRET: dev-jwt-secret-change-me
      CRYPTO_ENCRYPTION_KEY: <base64-32-byte-key>
      WORKER_BOOTSTRAP_TOKEN: worker-bootstrap-token
    ports:
      - '8080:8080'
    restart: unless-stopped
```

> Replace \<AUTHENTA_ACCOUNT_ID\> and \<tag\> with the values provided by Authenta Support. `AUTH_JWT_SECRET` and `CRYPTO_ENCRYPTION_KEY` must be replaced with real secrets before anything beyond local testing — the API server will fail to start in production mode without them set explicitly.

### ML Task Runner Settings

| Parameter                | Description                                                                   | Default                   |
| -------------------------- | -------------------------------------------------------------------------------- | --------------------------- |
| `LOG_FORMAT`               | Log output format (`pretty` or `json`)                                          | `pretty`                    |
| `LOG_LEVEL`                | Logging verbosity                                                                | `DEBUG`                    |
| `AUTHENTA_API_URL`         | Base URL of the API server the worker registers and polls against               | `http://api-server:8080`   |
| `WORKER_BOOTSTRAP_TOKEN`   | Must match the API server's `WORKER_BOOTSTRAP_TOKEN`                            | —                            |
| `WORKER_INSTANCE_ID`       | Stable identity for this worker instance — must be unique per running instance  | worker hostname (if unset) |
| `WORKER_CAPABILITIES`      | Comma-separated list of task types this worker can run (informational metadata) | auto-detected from `tasks/` |
| `FILE_URI_PREFIX`          | Prefix prepended to relative `file://` job URIs to resolve them on this host    | (empty)                     |

> ⚠️ `FILE_URI_PREFIX` is resolved **inside the worker container**, not on the host. It must match a path that's actually mounted in `ml-task-runner-gpu` — currently the compose file only mounts `./shared:/app/shared` and `./demo-app/data:/app/data`, so a default of `/opt/authenta` won't resolve to either unless you also mount a volume at that path. Set this to `/app/shared` (or add a matching volume mount) so relative `file://` URIs actually resolve.

### GPU Settings

The worker requires the NVIDIA Container Toolkit on the host:

```yaml
services:
  ml-task-runner-gpu:
    <<: *ml-task-runner-configs
    platform: linux/amd64
    image: <AUTHENTA_ACCOUNT_ID>.dkr.ecr.us-east-1.amazonaws.com/ml-task-runner:<tag>
    runtime: nvidia
    depends_on:
      - api-server
    environment:
      <<: *env
      NVIDIA_VISIBLE_DEVICES: all
      NVIDIA_DRIVER_CAPABILITIES: compute,utility
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
```

> Replace \<AUTHENTA_ACCOUNT_ID\> and \<tag\> with the value provided by Authenta Support. This ID refers to Authenta's private AWS account where the official container images are hosted.

## 4. Data Management

### Shared Volume Structure

```
./shared/
  ├── <job-id>/
  │   ├── result.json         # Detection results
  │   └── heatmaps-results/   # Visual detection maps
```

### Volume Configuration

```yaml
volumes:
  - ./shared:/app/shared # Maps host directory to container
```

## 5. Scaling Configuration

To run multiple inference containers:

```bash
docker compose up -d --scale ml-task-runner-gpu=3
```

> ⚠️ Give each replica a unique `WORKER_INSTANCE_ID` before scaling — see the [scaling caveat](/on-prem/architecture#scalability) in the architecture guide. Ensure sufficient hardware (GPU) resources are available before scaling up.
