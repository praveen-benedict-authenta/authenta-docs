# Maintenance & Updates

## Overview

This guide provides best practices for maintaining, monitoring, and updating **Authenta On-Prem** after deployment.
Authenta is designed for long-term, stable operation in air-gapped environments with minimal maintenance overhead.
You'll only need to enable temporary internet access when applying updates or pulling new container versions.

## 1. Log Management

The API server emits structured JSON logs (Winston); the ML Task Runner emits structured logs in `pretty` or `json` format depending on `LOG_FORMAT`.

### View Logs in Real Time

```bash
docker compose logs -f api-server
docker compose logs -f ml-task-runner-gpu
docker compose logs -f postgres
```

You'll see entries such as:

```json
// Worker job leased
{
  "id": "101",
  "version": 1,
  "op": { "slug": "faceswap-detection", "parameters": {} },
  "inputs": [
    { "slotName": "primary", "contentType": "video/mp4", "uri": "file:///app/shared/101/input/video.mp4" }
  ],
  "output": { "uri": "file:///app/shared/101/output/" }
}

// Job completion reported
{
  "id": "101",
  "status": "success",
  "result": { "confidence": 0.9821, "classification": "deepfake" }
}
```

### Save Logs to a Host Directory

You can map container logs to a persistent host directory by adding a volume to `docker-compose.yml`:

```yaml
services:
  ml-task-runner-gpu:
    volumes:
      - ./logs/ml-task-runner:/app/logs
  api-server:
    volumes:
      - ./logs/api-server:/app/logs
```

This allows you to:

- Retain logs across container restarts
- Integrate with centralized logging systems (ELK, Splunk, Datadog, Loki, etc.)
- Perform local audits and monitoring

### Log Format and Environment Settings

The following environment variables control logging and worker behavior (`x-env` in `docker-compose.yml`):

| Variable                  | Description                                                        | Default in compose        |
| --------------------------- | --------------------------------------------------------------------- | --------------------------- |
| `LOG_FORMAT`               | ML Task Runner log output format (`pretty` or `json`)                | `pretty`                    |
| `LOG_LEVEL`                | ML Task Runner log verbosity                                          | `DEBUG`                     |
| `AUTHENTA_API_URL`         | API server URL the worker registers and polls against                | `http://api-server:8080`   |
| `WORKER_BOOTSTRAP_TOKEN`   | Shared secret — must match `WORKER_BOOTSTRAP_TOKEN` on `api-server`   | —                            |
| `WORKER_INSTANCE_ID`       | Stable identity for this worker — must be unique per running instance | —                            |
| `WORKER_CAPABILITIES`      | Task types this worker advertises (informational)                     | —                            |
| `FILE_URI_PREFIX`          | Prefix prepended to relative `file://` job URIs                       | —                            |

Logs include:

- Job leases and completion reports
- Model inference results and confidence scores
- Worker registration and re-registration events
- Error conditions and exceptions

## 2. Monitoring & Health Checks

To ensure continuous operation, periodically verify container and service status.

### Check Container Status

```bash
docker compose ps
```

Expected output:

```
postgres              Up  (port 5432)
api-server            Up  (port 8080)
ml-task-runner-gpu    Up
```

### Check API Server Health

```bash
curl http://localhost:8080/api/v1/health/ready
```

This checks both database and storage connectivity.

### Inspect the Worker Fleet

- List registered workers (requires a platform-`operator` token):
  ```bash
  curl http://localhost:8080/api/v1/workers -H "Authorization: Bearer <operator-token>"
  ```
- Each entry shows `lastSeenAt`, `isStale` (no activity in >5 minutes), and the job it's currently processing, if any
- If a worker never appears, check `docker compose logs -f ml-task-runner-gpu` for registration errors (usually a `WORKER_BOOTSTRAP_TOKEN` mismatch)

### Check Postgres

```bash
docker compose exec postgres pg_isready -U authenta
```

### Check System Logs

Inspect system-level Docker logs for any restarts or errors:

```bash
sudo journalctl -u docker --since "1 hour ago"
```

## 3. Scaling & Performance Optimization

Authenta supports horizontal scaling for increased throughput.

### Add More Inference Containers

```bash
docker compose up -d --scale ml-task-runner-gpu=3
```

> ⚠️ **`WORKER_INSTANCE_ID` must be unique per replica.** The API server treats `instanceId` as a worker's stable identity — a duplicate ID causes each new registration to delete the previous worker record (and release its in-flight job back to the queue). The `x-env` anchor in `docker-compose.yml` sets a single static `WORKER_INSTANCE_ID`, which is fine for one replica but must be overridden per-container before scaling. Ensure you also have enough GPU/CPU/RAM headroom before scaling up.

### Scale Down or Restart

```bash
docker compose down
docker compose up -d --scale ml-task-runner-gpu=1
```

Scaling can be adjusted dynamically without data loss — in-flight jobs from a stopped worker are automatically released back to the queue (see [Architecture](/on-prem/architecture)).

## 4. Updating Authenta

Authenta releases updates periodically that include:

- Improved AI models
- Security and stability patches
- API server feature and schema updates

Because the system is offline, updates require temporary internet access.

### Steps to Update

1. Enable internet access on the host
2. Re-authenticate to the private ECR:
   ```bash
   aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin <AUTHENTA_ACCOUNT_ID>.dkr.ecr.us-east-1.amazonaws.com
   ```
3. Pull updated images and re-run migrations if the update notes call for it:
   ```bash
   docker compose pull
   # From the authenta-api-server source checkout, if migrations are required:
   DATABASE_URL=postgres://authenta:<password>@localhost:5432/authenta bun run db:migrate
   ```
4. Restart services:
   ```bash
   docker compose down && docker compose up -d
   ```
5. Disable internet access again for air-gapped operation

### Verifying the Update

```bash
docker images | grep -E 'authenta-webapp|ml-task-runner'
```

If the image tags/digests reflect the update you pulled, deployment is complete.

## 5. ECR Credentials Management

Authenta provides read-only AWS ECR credentials for image access.
These can safely be:

- Stored in your CI/CD or secret manager
- Revoked and reissued after initial deployment if required

Credentials are only needed when:

- Pulling images for the first time
- Performing updates

They are not required for day-to-day operation.

## 6. Backup & Recovery

### Back Up Important Data

| What                          | How                                                                                          | Purpose                        |
| ------------------------------ | ----------------------------------------------------------------------------------------------- | --------------------------------- |
| Postgres database              | `docker compose exec postgres pg_dump -U authenta authenta > backup.sql`                        | Users, tenants, jobs, artifacts, billing |
| `postgres-data` volume         | `docker run --rm -v authenta-on-prem_postgres-data:/data -v $(pwd):/backup alpine tar czf /backup/postgres-data.tgz /data` | Raw volume snapshot (alternative to `pg_dump`) |
| `./shared`                     | Standard file copy / rsync                                                                       | Local job input/output files   |
| `docker-compose.yml`           | Standard file copy / version control                                                             | Deployment configuration       |

> 💡 Regular backups ensure quick recovery in case of system failure. Prefer `pg_dump` for portability across Postgres versions.

### Restore Procedure

1. Restore `docker-compose.yml` and the `./shared` directory from your backup
2. Bring up `postgres` alone, then restore the dump:
   ```bash
   docker compose up -d postgres
   cat backup.sql | docker compose exec -T postgres psql -U authenta authenta
   ```
3. Start the rest of the stack:
   ```bash
   docker compose up -d
   ```

## 7. Resource Cleanup

To remove unused or old images and free disk space:

```bash
docker image prune -a
```

To clear stopped containers and unused volumes:

```bash
docker system prune -a --volumes
```

> ⚠️ Ensure you have backups before pruning — `docker system prune --volumes` will delete the `postgres-data` volume if it isn't attached to a running container. These commands delete unreferenced data permanently.

## 8. Security Maintenance

Authenta On-Prem is fully self-contained and runs offline, but it's still recommended to:

- Restrict the `postgres` (`5432`) and `api-server` (`8080`) ports to trusted hosts only — don't expose them publicly
- Rotate `AUTH_JWT_SECRET`, `CRYPTO_ENCRYPTION_KEY`, `WORKER_BOOTSTRAP_TOKEN`, and `POSTGRES_PASSWORD` periodically
- Keep Docker and host OS up to date with security patches
- Run containers as non-root users if your security policy requires it

> 🔐 No external telemetry, logging, or network connections are made — Authenta operates fully within your environment.

## 9. Troubleshooting Common Issues

| Symptom                        | Possible Cause                                | Recommended Action                                           |
| -------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------- |
| Containers exit unexpectedly    | Insufficient resources or missing required env vars | Check `docker compose logs`; `api-server` exits immediately if secrets like `AUTH_JWT_SECRET` aren't set |
| Worker never appears in `/api/v1/workers` | `WORKER_BOOTSTRAP_TOKEN` mismatch between `api-server` and `ml-task-runner-gpu` | Confirm both services use the same value in `docker-compose.yml` |
| Jobs stuck in `queued`          | No healthy worker registered, or worker crashed after registering | `docker compose logs -f ml-task-runner-gpu`; restart the service |
| GPU not detected                | Missing or incompatible drivers                  | Reinstall NVIDIA drivers and container toolkit                 |
| Update fails                    | Old credentials or network block                 | Re-authenticate and re-enable outbound internet temporarily     |

## 10. Lifecycle Checklist

| Maintenance Task  | Frequency               | Action                                                        |
| ------------------- | -------------------------- | ------------------------------------------------------------------ |
| Log review          | Weekly                    | Inspect `api-server` and `ml-task-runner-gpu` logs for errors/anomalies |
| Database backup     | Weekly                    | `pg_dump` the `postgres` service (Section 6)                  |
| Update pull         | Quarterly or as advised  | Temporarily enable internet and update images                  |
| Secret rotation     | Quarterly                 | Rotate `AUTH_JWT_SECRET`, `CRYPTO_ENCRYPTION_KEY`, `WORKER_BOOTSTRAP_TOKEN`, `POSTGRES_PASSWORD` |
| Resource cleanup    | Quarterly                 | Prune unused images and containers                              |

## Summary

| Aspect             | Description                                                    |
| -------------------- | ------------------------------------------------------------------ |
| Logs                | Structured JSON/pretty logs, can be exported to central systems |
| Updates             | One-time internet required to pull new images (and possibly migrate the database) |
| Scaling             | Add more task runners for parallel processing (unique `WORKER_INSTANCE_ID` per replica) |
| Security            | Offline mode, no telemetry, rotatable secrets                    |
| Maintenance Effort  | Minimal — designed for stable long-term operation                |
