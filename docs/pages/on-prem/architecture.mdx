# System Architecture

## Overview

Authenta On-Prem is built as a **modular, containerized system** that can run entirely within your organization's network.
All inference processing, job orchestration, and result storage happen locally — ensuring full data confidentiality and compliance.

At its core, Authenta consists of three primary components:

1. **PostgreSQL** — Relational database that backs the API server: users, tenants, jobs, artifacts, billing, and the job queue itself
2. **Authenta API Server** — Central backend that manages authentication, job lifecycle, artifact storage, and the worker fleet
3. **ML Task Runner** — Python-based container that registers with the API server, polls for queued jobs, and executes the AI models (GPU-accelerated)

These components communicate internally through a secure local Docker network.
Once deployed, the system can run indefinitely in an **air-gapped (offline)** mode.

## Component Details

### 🐘 PostgreSQL (Database & Job Queue)

- Single data store for relational data, sessions, and the job queue — no Redis or message broker required
- The job queue uses `SELECT FOR UPDATE SKIP LOCKED` so multiple workers can claim jobs concurrently without a dedicated broker
- Runs as the `postgres` service; data persists in a named Docker volume (`postgres-data`) across restarts

### 🌐 Authenta API Server (Orchestration Service)

- NestJS backend that handles auth (JWT + worker tokens), tenants, task types, billing, and the job/artifact lifecycle
- Accepts job creation and file uploads from client applications
- Exposes the worker fleet API — registration, job leasing, and completion reporting — consumed by the ML Task Runner
- Runs as the `api-server` service, listening on port `8080`

### 🧠 ML Task Runner (Inference Service)

- Containerized Python service that loads Authenta's trained models
- On startup, registers itself with the API server using a shared bootstrap token, then polls for queued jobs over HTTP (register → lease → process → complete)
- Runs as the `ml-task-runner-gpu` service, optimized for NVIDIA GPU acceleration
- Writes inference outputs and logs to the shared host directory
- Scalable: multiple task runner containers can be deployed for parallel job handling (see [Scaling](#scalability) below for an important caveat)

### 📂 Shared Host Volume

- Mounted as a local directory on the host system (e.g., `./shared` → `/app/shared`)
- Used for local input/output file exchange with the ML Task Runner when jobs reference on-disk paths (`FILE_URI_PREFIX`)
- Ensures content stays within your environment with no external storage dependency

## Internal Communication

- All services communicate over an internal **Docker network**, addressed by service name (`postgres`, `api-server`)
- The ML Task Runner talks to the API server over plain HTTP within the Docker network (`http://api-server:8080`)
- Only the ports you explicitly publish are reachable from outside the host — currently `api-server` (`8080`) and `postgres` (`5432`, useful for running migrations from the host)
- You can further isolate services using your own network namespace or container firewall rules

## Offline Operation

After the initial image pull from Authenta's private AWS ECR (and the public `postgres` image), all components can run offline:

- No outbound API calls or telemetry
- No internet connection required for inference, job orchestration, or logging
- Optional network hardening:
  - Block all outbound traffic
  - Allow only internal container-to-container communication

This ensures complete data isolation and compliance for secure or regulated environments.

## High-Level Data Flow

1. A client application creates a job and uploads the input file through the Authenta API Server
2. The job is queued in PostgreSQL (`status = queued`)
3. The ML Task Runner registers with the API server (bootstrap token) and continuously polls the lease endpoint
4. When a job is available, the worker leases it, resolves the input (local file path or downloaded artifact) into its job workspace, and runs the appropriate detection model
5. The resulting metadata, detection scores, and any output artifacts are reported back to the API server via the completion endpoint
6. The API server persists the result; clients retrieve it through the job/artifact API

## Scalability

You can deploy multiple ML Task Runner containers to increase throughput; each instance registers independently and polls for its own jobs.

```bash
docker compose up -d --scale ml-task-runner-gpu=3
```

> ⚠️ **Important:** `WORKER_INSTANCE_ID` must be unique per running instance. The API server treats `instanceId` as the worker's stable identity — re-registering with an ID that's already in use deletes the existing worker record (and releases its in-flight job back to the queue). Scaling with a single static `WORKER_INSTANCE_ID` shared across replicas will cause them to continuously evict one another. Give each replica its own ID (e.g., derive it from the container hostname, or override `WORKER_INSTANCE_ID` per replica) before scaling beyond one instance.

## Summary

| Aspect          | Description                                              |
| ---------------- | --------------------------------------------------------- |
| Deployment Type | Docker Compose                                            |
| Core Services   | PostgreSQL, Authenta API Server, ML Task Runner            |

| Scalability     | Multi-instance ready (unique `WORKER_INSTANCE_ID` per replica required) |
| Security        | Offline-capable, isolated, no external dependencies once deployed |
